## High impact

### 1. Backtest has survivorship bias — results are inflated
`backtest.py:58` — `walk_forward()` calls `fetch_sp500()` once, which scrapes **today's** S&P 500 membership from Wikipedia, then applies it to 2015–2024. Companies that got delisted or dropped from the index (the losers) are excluded; companies added later (the winners, post-run-up) are included for their whole history. Momentum backtests are especially sensitive to this — your Sharpe/total return numbers are optimistic, possibly substantially.

A second layer: `backtest.py:84-90` drops any symbol whose exit price can't be fetched from the period average. A stock that gets delisted mid-period (usually catastrophic for longs) silently vanishes instead of registering its loss.

**Fix:** use a point-in-time membership dataset (historical S&P 500 constituents lists are freely available on GitHub), or at minimum label results "survivorship-biased — upper bound" so future-you doesn't trust the numbers.

### 2. `vix_score()` is the only gate signal with no error fallback
`macro_gate.py:8-12` — every other signal catches exceptions and degrades to neutral 50.0. `vix_score()` has no try/except, so one yfinance hiccup on `^VIX` crashes `compute_gate()` → `gate`, `scan`, `review`, `recommend`, and `rebalance` all die. Inconsistent with the design of the other five signals.

Also methodological: the score is relative to the trailing 1-year max. After a calm year (max VIX ≈ 20), VIX 18 scores ~10/100 ("extreme fear") despite being objectively low. After a crash year (max ≈ 60), VIX 30 scores 50. Consider absolute bands or a percentile rank like `credit_spread_score` uses.

### 3. `recommendations.review_id` is never populated — dead join
- `review.py:149` — `review_candidates()` returns a DataFrame with no `review_id` column
- `db.py:177-198` — `save_reviews()` inserts rows but doesn't return the generated IDs
- `recommendation.py:338` — `row.get("review_id")` is therefore always `None`
- `db.py:278` — `load_latest_recommendations()` LEFT JOINs reviews on `review_id` to fetch `claude_summary` — **never matches**

Net effect: the Claude summary is silently missing anywhere recommendations are loaded back from the DB (Recommendation dashboard page). Fix: have `save_reviews` return `{symbol: review_id}` and thread it through.

### 4. Analyst agent loop mishandles `max_tokens` stop reason
`analyst.py:299-317` — `run_turn()` only handles `end_turn` and `tool_use`. If a response stops with `max_tokens` (likely with `thinking` enabled and `max_tokens=2048`), neither branch matches, nothing is appended to `messages`, and the loop **re-sends the identical request** up to `ANALYST_MAX_TURNS` times — burning tokens for nothing. Separately, if the model is still calling tools when turns run out, the function returns `assistant_text = ""` (blank chat reply). Handle `max_tokens` explicitly and synthesize a fallback message when turns exhaust.

### 5. Momentum accepts 10 bars as "12-month momentum"
`scanner.py:17` — `compute_momentum()` only requires `len(hist) >= 10`. A stock with 3 weeks of trading history (recent IPO/spinoff) gets a "12-1 momentum" computed over days, then ranked against real 12-month figures in the sector percentile. Also `iloc[0]`/`iloc[-1]` assume the fetched window actually spans t-12mo → t-1mo; for short histories `iloc[0]` is just the IPO date. Require the first bar to be within ~2 weeks of `t12`, else return `None`.

## Medium

### 6. Same-day re-run leaves stale recommendation rows
`db.py:201-263` — upsert is by (UTC date, rank). If a morning run produced 3 recs and an afternoon re-run produces 1, ranks 2–3 from the morning survive and `load_latest_recommendations()` returns a mixed batch. Delete today's rows (or the batch) before insert.

### 7. `deep_dive_ticker` fabricates data and pollutes the reviews table
`analyst.py:107-123` — hardcodes `score: 50.0`, `gate_sizing: 0.6`, sector "Unknown", then saves the review attached to the **latest unrelated scan_id**. That review now looks like a scan-derived review in any later query/postmortem. Either don't persist deep-dives, or add a `source` column.

### 8. DST approximation in `_fetch_current_price`
`recommendation.py:135` — `et_offset = -4 if 3 <= month <= 11 else -5` is wrong for early March (pre-2nd-Sunday) and most of November. Sessions get mislabeled (pre-market/after-hours). Python ships `zoneinfo`: `datetime.now(ZoneInfo("America/New_York"))` — strictly better, no dependency.

### 9. Mild lookahead in backtest price fallback
`backtest.py:28` — when no price exists at/before `target_date`, `_get_price` returns `hist.iloc[0]`, the first price **after** the date. For entries this fills at a future price. Return `None` instead and let the symbol drop.

### 10. `refresh_recommend` recomputes the gate mid-pipeline
`actions.py:87` — after scan+review (several minutes), `compute_gate()` runs again with fresh network fetches. The recommendation can use a different gate than the scan it's based on (e.g. scan ran at PARTIAL, recs sized at FULL). Thread the gate from `refresh_scan` through instead — also saves ~30s of redundant fetches.

### 11. Trade-log hygiene (small, cheap fixes)
- `tradelog.py:81-116` — `edit_trade` can set `exit_price` without setting `closed_at` → closed trade with NULL close date in postmortem output
- `tradelog.py:119-124` — `delete_trade` orphans `trade_outcomes` rows (FKs declared but never enabled: no `PRAGMA foreign_keys=ON` in `db.py:10`)
- `cli.py:249` — display bug: prints "Blended score: X/10" but blended is 0–100

### 12. Review JSON parsing is fragile
`review.py:121-126` — `json.loads(response.content[0].text)` fails if the model wraps output in ```json fences, and the candidate is silently skipped (you get <6 reviews with only a console warning). You already use the robust pattern in `recommendation.py` — forced `tool_choice` with a schema. Port it here.

## Performance (biggest practical win)

### 13. Sequential per-ticker fetches: scan ~3 min, backtest hours
- `scanner.py:16` — `score_universe` makes ~503 sequential `yf.Ticker(s).history()` HTTP calls
- `walk_forward` repeats that for every rebalance period (~260 periods × 500 symbols)

`yf.download(symbols_list, start=..., end=..., group_by="ticker")` fetches in batched/threaded mode. For the backtest: download the full 2015–2024 panel **once**, then compute momentum per period by slicing locally. Realistic outcome: scan 3 min → ~10s; backtest "10–30 min" (optimistic) → ~2 min. This also makes the survivorship fix (#1) cheap to iterate on.
